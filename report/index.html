一执行摘要

本次对云端看板做了一次全链路整体检查：从登录鉴权、26 个业务接口、 PostgreSQL 库内数据一致性，一直到前端页面在真实浏览器里的表现，逐层交叉核对。

结果是体检通过，但过程中揪出了 2 个真实缺陷 —— 都不是崩溃型问题， 而是「数字看着对、其实口径错了」的隐蔽类型，只在特定条件下暴露：

  1. 快照日期在东八区整体回退一天：首页「客户平台未回款」显示 2026-09-20， 而库里最新快照是 2026-09-21。读者会以为这条数据是昨天的。
  2. 从未登录过的人第一次打开会看到「登录已过期」：让人误以为账号出了问题， 实际只是还没登录。
为什么第一个缺陷差点被漏掉

上一轮已经修过同类的日期缺陷，但只改了其中一处（同步状态的数据源汇总）， 客户平台那一整块没跟着改。纯接口层面的自动化检查「合计金额对得上就算过」，查不出日期错； 这次是靠真实浏览器截图肉眼比对才发现的。因此本轮把「所有接口暴露的快照日期 vs 库内真实最新快照」做成了固定回归断言，覆盖 14 处，以后再漏会立刻失败。

二发现的两个缺陷与修复

缺陷 1 · 快照日期在东八区回退一天 （已修复）

现象 首页「数据源明细」里客户平台未回款显示 2026-09-20，另两个数据源显示 2026-09-21； 客户平台相关页面的日期与 Excel 导出文件名同样少一天。
根因 PostgreSQL 的 DATE 列被 pg 读成 本地零点的 JS Date； 再经 new Date(x).toISOString() 换算成 UTC，东八区就会整体退一天。
上一轮只修了 collectSources()，receivable.js 里客户平台那块剩下的 5 处（getCpuLatestSnapshot() + summary / breakdown / detail / 导出文件名）继续错， 而首页卡片恰好读的正是 /api/customer-platform-unpaid/summary。
影响面 首页卡片与数据源明细、客户平台三个查询接口、两个 Excel 导出文件名。金额与行数都是对的，只有日期错，所以极难被数值校验发现。
修复 把日期口径收敛到唯一出处 server/utils/date.js；SQL 侧优先直接 to_char(col,'YYYY-MM-DD') 取字符串，不再二次换算。
连带修复 同一类隐患还有 6 处：watcher.js×2、scheduler.js、 importer.js×2、import-excel.js 用 new Date().toISOString().slice(0,10) 取「今天」—— 北京时间 00:00–08:00 之间 会比本地日期少一天，深夜同步会把快照记成昨天，现已统一改为本地日期。

修复前后对比（问题在「多绕了一道 UTC 换算」）：

// ✗ 错误：DATE 列 → Date → UTC，东八区退一天
snapshotDate: new Date(snapshot).toISOString().slice(0, 10)
// 2026-09-21 变成 "2026-09-20"
// ✓ 正确：SQL 里直接取字符串，不做任何时区换算
SELECT to_char(MAX(snapshot_date),'YYYY-MM-DD') AS d FROM customer_platform_unpaid
// 拿到就是 "2026-09-21"，直接返回
snapshotDate: snapshot

缺陷 2 · 冷启动误报「登录已过期」 （已修复）

现象 从未登录过的浏览器第一次打开系统，页面右下角弹出红色提示「登录已过期，请重新登录」， 但用户其实压根还没登录过，看到提示会以为账号异常。
根因 前端启动时会调用 getMe() 查询登录状态，未登录时后端返回 401 —— 这是设计行为。 但全局 401 拦截器不区分「带了令牌却被拒」和「压根没带令牌」，一律弹「已过期」。
修复 请求拦截器记录本次请求是否真的带了令牌（config.__sentToken）， 只有带着令牌却被拒才提示过期；没带令牌就静默跳转登录页。
验证 真实浏览器三条路径全部覆盖：冷启动不弹提示 / 正常登录不误报 / 坏令牌正常提示并清空令牌。

六日期口径铁律（本次最重要的结论）

本项目大量使用 DATE 列做「每日快照」，这类值有两个经典陷阱。 本次已把两条铁律在代码层面统一落地，并写成回归断言。

陷阱一：DATE 列不能经 toISOString()

PostgreSQL 的 DATE 被 pg 读成本地零点的 Date， 转成 UTC 后东八区整体退一天。

// ✗ 2026-09-21 会变成 "2026-09-20"
new Date(x).toISOString().slice(0, 10)
陷阱二：「今天」不能用 UTC 日期

new Date().toISOString().slice(0,10) 是 UTC 日期， 北京时间 00:00–08:00 之间会比本地日期少一天 —— 深夜同步会把快照记成昨天。

// ✗ 北京时间 9/22 凌晨 1 点，会得到 "2026-09-21"
new Date().toISOString().slice(0, 10)

统一做法

场景做法
能在 SQL 里取优先 to_char(col,'YYYY-MM-DD')，直接拿字符串
需要在 JS 里转换统一走 server/utils/date.js 的 toDateOnly()（取本地日历字段，不做时区换算）
需要「今天」todayDate() —— 本地日期，不是 UTC 日期
禁止全项目不再手写 toISOString().slice(0,10) 处理快照日期
不要混淆：业务日期是另一条链路

从 Excel 读入、经 SheetJS 序列号换算的业务日期（doc_date / order_date） 本身按 UTC 序列口径解析，属另一条链路，不要和「快照日期」一起改。 本次只对其中「字符串日期」这一分支做了加固：源里若有 2026/9/21 这类月份不补零的写法， 旧逻辑会按本地零点解析又少一天，现已统一走 toDateOnly()。

防止复发

体检脚本新增固定断言「快照日期全面对齐」：把所有暴露 snapshotDate 的接口 （当前 14 处）与库内真实 MAX(snapshot_date) 一一比对。 另有专项断言直接测 utils/date.js 对「DATE 列 / 斜杠 / 点号 / 补零与不补零」各种输入的稳定性。
